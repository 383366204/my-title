## ADR-0001：使用 GitHub Projects 作为项目执行工具

- **日期**：2026-09-14
- **状态**：Proposed
- **决策者**：成员 A、成员 B

### 背景

项目是 2 人团队的 Node.js / React 工具型项目，代码托管在 GitHub。需要同时管理任务、进度、风险和代码关联，但不能承担 Jira、Microsoft Project 等重型工具的维护成本。

### 决策

使用 GitHub Projects + Issues + Milestones 作为唯一任务执行系统，并在仓库 `docs/project-management/` 维护项目基线。

### 后果

**收益**

- 任务与 Issue、PR、提交天然关联。
- 免费、配置成本低，适合 2 人团队。
- 支持 Table、Board、Roadmap 视图。

**代价**

- 高级资源管理和成本管理能力有限。
- 需要团队纪律性地维护字段和状态。

### 复审条件

- 团队超过 5 人。
- 需要复杂跨团队依赖、发布火车或严格合规审计。

## ADR-0002：采用轻量 PMP，而不是完整瀑布或重型敏捷流程

- **日期**：2026-09-14
- **状态**：Proposed
- **决策者**：成员 A、成员 B

### 背景

项目存在外部依赖、浏览器自动化和质量合规风险，需要 PMP 的范围、风险、质量、沟通思维；但团队只有 2 人，不能承担大量会议和文档。

### 决策

保留项目章程、WBS、Backlog、风险登记册、决策记录、RACI、里程碑和验收标准；执行上使用 1-2 周迭代、每周计划会、每日异步同步和轻量评审。

### 后果

- 管理成本可控。
- 关键风险和范围变化可追溯。
- 不使用复杂甘特图、挣值分析和多层级审批。

### 复审条件

- 出现固定日期交付合同。
- 干系人数量显著增加。
- 需要正式合规审计。

## ADR-0003：任务必须有唯一 Owner 和明确验收标准

- **日期**：2026-09-14
- **状态**：Proposed
- **决策者**：成员 A、成员 B

### 背景

2 人团队容易默认“一起负责”，导致任务无人推进或验收标准不清。

### 决策

所有进入当前迭代的 Issue 必须有唯一 Owner、Priority、Size、Status 和验收标准。另一个成员负责评审或复核。

### 后果

- 责任边界清晰。
- 每周进度更容易判断。
- Owner 可以请求帮助，但不能把责任转移给未指定的人。

### 复审条件

- 引入新手成员或多团队协作。

## ADR-0004：外部平台风控状态只做结构化提示，不自动绕过

- **日期**：2026-09-14
- **状态**：Accepted
- **决策者**：项目现有约束与团队确认

### 背景

1688、淘宝、生意参谋可能出现登录、验证码、滑块、功能权限或限流状态。自动处理账号凭据和验证行为存在安全与合规风险。

### 决策

系统识别并返回结构化阻塞状态，向用户说明需要执行的人工动作；不自动输入密码、验证码，不自动拖动滑块。

### 后果

- 降低账号和安全风险。
- 流程可能需要人工干预。
- 用户体验设计必须清楚地给出下一步动作和重试入口。

### 复审条件

- 官方提供合法自动化能力或明确授权。

## ADR-0005：产品定位为电商全流程运营工具

- **日期**：2026-09-15
- **状态**：Accepted
- **决策者**：项目维护者

### 背景

项目初期以自动选品和标题生成作为切入点，但实际目标不是做一个单点选品工具，而是把电商运营中的重复性工作逐步自动化。选品只是运营全流程中的一个环节，后续还需要覆盖同行分析、1688 好店跟踪、订单执行表、评价跟踪表、批量素材处理等能力。

### 决策

将产品定位调整为“电商全流程运营工作台”。架构和项目管理均以运营环节、Workflow 编排、数据产物和人工复核点为中心，而不是只围绕选品和标题组织。

### 后果

**收益**

- 产品目标与真实运营场景一致。
- Workflow、Skill、表单和素材处理可以共享同一套运行时和数据模型。
- 新运营环节可以按标准切片持续接入。

**代价**

- 项目范围明显扩大，必须控制 2 人团队的并行度。
- 需要统一实体 ID、产物 Schema 和字段来源。
- 每个新环节都必须定义上下游、验收标准和人工复核点。

### 复审条件

- 某个运营环节需要独立产品化。
- 外部平台能力变化导致全流程工作台无法继续统一编排。

## ADR-0006：运营自动化必须保留合规与授权边界

- **日期**：2026-09-15
- **状态**：Accepted
- **决策者**：项目维护者

### 背景

全流程运营会涉及平台规则、订单、评价和素材处理。如果自动化越过合规边界，可能带来账号处罚和法律风险。

### 决策

1. 不提供虚假交易、刷单、操纵销量、刷评价或篡改排名的能力。
2. 订单相关功能仅支持真实订单执行、发货、售后和复盘跟踪。
3. 评价相关功能仅支持真实评价跟踪、合规回复建议和售后改进。
4. 素材批量处理仅面向用户拥有合法处理权的素材，必须保留来源和授权标记。
5. 不自动输入密码、验证码，不自动拖动滑块，不绕过平台风控。

### 后果

- 系统保留关键人工复核和授权确认点。
- 某些需求会被明确拒绝或要求改为合规表达。
- 数据模型需要记录来源、授权状态、人工动作和处理结果。

### 复审条件

- 官方提供明确授权的自动化能力。
- 法律顾问或平台规则给出新的合规解释。

## ADR-0007：以统一任务中心作为运营流程集成骨架

- **日期**：2026-09-15
- **状态**：Proposed
- **决策者**：项目维护者

### 背景

项目正在扩展关键词监控、异常中心、单店月度净利润核算、活动日历、运营表单、素材处理和 SOP。若每个流程都单独提示用户，待办会散落在画布节点、日志和本地文件中，用户难以判断优先级，也无法追溯处理结果。

### 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 每个流程独立提醒 | 实现简单 | 待办分散，重复提醒，难以复盘 |
| 只做异常列表 | 覆盖异常场景 | 无法承接人工确认、SOP、活动准备和优化建议 |
| 统一任务中心 | 单一入口，可去重、分级、追踪和复盘 | 需要先定义稳定任务契约 |

### 决策

引入统一任务中心，所有需要人工确认、延期处理、异常响应或后续跟进的流程都生成标准化任务。任务必须关联来源、实体、证据、建议动作、状态和审计记录。异常中心负责事件去重和分级，再生成或更新任务。

### 后果

**收益**

- 用户只需要在今日待办和高风险视图中处理工作。
- 不同流程共享任务状态、优先级、负责人和审计模型。
- 可以统计任务来源、处理时长、超期率和忽略率，反哺流程优化。

**代价**

- 必须先完成 Task Schema 和状态流设计。
- 各流程不能再私自定义互不兼容的待办结构。
- 需要处理任务去重、状态冲突和审计存储。

### 复审条件

- 任务量或来源规模超过当前模型的承载能力。
- 需要多人协作派单、权限隔离或跨店铺任务队列。
