# Backlog 与 WBS

- **版本**：v1.3
- **更新日期**：2026-09-15
- **执行工具**：GitHub Issues + GitHub Projects
- **团队容量**：2 人
- **定位**：电商全流程运营工具，而不是单一选品工具
- **原则**：Backlog 只保留有可能在近期执行的任务；长期想法放入 `Icebox`，不占当前迭代注意力。

## 4. 优先级定义

| 优先级 | 定义 | 处理要求 |
|---|---|---|
| P0 | 阻塞主流程、质量底线、合规底线、任务骨架或发布 | 本迭代必须处理 |
| P1 | 明显提升可用性或降低维护成本 | 排入最近 1-2 个迭代 |
| P2 | 有价值但可延后 | Backlog 保留，等待容量 |
| P3 | 想法或机会型工作 | Icebox，暂不估算 |

## 5. 规模估算

| 规模 | 预估工作量 | 复杂度示例 |
|---|---|---|
| S | 0.5 人日内 | 文档、小修复、字段补充 |
| M | 1-2 人日 | 单模块功能、中等测试 |
| L | 3-5 人日 | 跨模块改造、流程恢复 |
| XL | 超过 5 人日 | 必须拆分，不允许直接进入 Ready |

## 6. Definition of Ready

任务进入 `Ready` 前必须满足：

1. 所属运营环节和上下游产物清楚。
2. 用户价值或问题背景清楚。
3. 明确验收标准。
4. 涉及的模块或文件范围明确。
5. 规模为 S / M / L；XL 必须继续拆分。
6. 外部依赖、账号条件、素材授权、合规风险已标注。
7. 如果会生成运营任务，明确任务类型和人工复核点。
8. 有唯一 Owner。

## 7. Definition of Done

任务进入 `Done` 前必须满足：

1. 代码实现完成，未提交无关改动。
2. 相关单元 / 集成测试更新并通过。
3. 至少一名非作者完成评审。
4. 用户可见行为更新文档或 README。
5. 错误路径、降级路径、人工复核路径和日志可诊断。
6. 不包含密钥、Cookie、临时文件和调试输出。
7. 涉及素材处理时，授权检查和处理记录可追溯。
8. 涉及平台操作时，不绕过风控，不做虚假交易或评价操纵。
9. 涉及异常或任务时，事件、任务、实体和审计记录可关联。
10. 涉及单店月度净利润核算时，真实值、预估值、缺失数据和固定费用分摊规则必须分开表达。
11. GitHub Issue 关联 PR 或提交记录。
12. 若影响里程碑或风险，更新对应管理文档。

## 8. 每周维护流程

1. 新需求先进入 `Backlog`，并标注所属运营环节。
2. 周计划会评审优先级、规模、风险、合规边界和容量。
3. 只将本迭代能完成的任务移动到当前 Iteration。
4. 每周五清理过期任务，更新本页 Epic 状态。
5. 连续两个迭代未动的 P2 任务降级到 Icebox 或关闭。
