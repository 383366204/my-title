# 风险登记册

- **版本**：v1.3
- **更新日期**：2026-09-15
- **评审频率**：每周一次；重大外部变化或新增运营环节时立即更新
- **责任人**：成员 A 维护，成员 B 复核；每条风险必须有唯一 Owner

## 1. 风险评分规则

- **概率**：1 低、2 中、3 高
- **影响**：1 低、2 中、3 高
- **风险值** = 概率 × 影响
- **等级**：
  - 1-2：低
  - 3-4：中
  - 6-9：高

## 3. 风险应对策略

| 策略 | 适用场景 | 示例 |
|---|---|---|
| 规避 | 高风险且违反边界的需求 | 拒绝刷单、刷评价、绕过风控、处理未授权素材 |
| 减轻 | 可通过设计降低概率或影响 | API 客户端封装、重试、mock 测试、授权检查 |
| 转移 | 依赖外部服务承诺 | 使用官方 API、付费额度或备用模型 |
| 接受 | 影响低或成本高于收益 | 低频页面样式变化导致的提示信息不完美 |
| 升级 | 超出成员处理能力 | 需要账号权限、素材授权、采购或业务决策 |

## 4. 风险升级规则

1. 风险值达到 6 且没有明确应对方案，当天在周同步渠道提出。
2. 阻塞主流程超过 1 个工作日，改为 Issue 并标记 `risk` 与 `priority: P0`。
3. 需要花钱、变更账号权限、确认素材授权或调整范围，记录到决策日志。
4. 每周评审一次 Open 风险；连续三周无变化且无动作的风险重新评估是否关闭。

## 6. 风险看板映射

- 高风险 Issue：`Risk = High`
- 中风险 Issue：`Risk = Medium`
- 低风险 Issue：`Risk = Low`
- 只跟踪风险本身的工作：`Work Type = risk`
- 涉及平台规则或素材授权的任务：`Work Type = compliance`
- 高风险任务必须写明缓解动作和复核人。
- 统一任务中心的产品内任务不要与 GitHub Project 的开发 Issue 混用。
